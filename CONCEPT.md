# CONCEPT.md — мой разбор магазина

## 1. API, REST и группы эндпоинтов

API это интерфейс для взаимодействия с приложением(бэкенд сайта, ИИ, почты, погода и т.д). Не всегда компании предоставляют API, как правило если они хотят чтобы с их сервисом общались только через определенный клиент( их же фронтенд, мобильное приложение) - API может быть закрытым.

REST это архитектурный стиль для взаимодействия между клиентом и сервером. REST это набор правил, которые могут быть не полностью соблюдены, либо вовсе не соблюдены (gRPC, SOAP не являются REST). Так же API, которое для всех своих эндпоинтов использует только POST( для получения, удаления, создания, обновления) не будет считаться RESTfull.

Набор правил, которые показывают уровень соответствия стандарту REST:

Client–server: клиент и сервер разделены и развиваются независимо.
Stateless: каждый запрос несёт всё нужное для его обработки, сервер не хранит состояние сессии клиента между запросами.
Cacheable: ответы явно помечаются как кэшируемые или нет.
Uniform interface: единый интерфейс. Включает идентификацию ресурсов через URI, работу с ресурсами через их представления (JSON, XML), самоописывающие сообщения (метод, заголовки, Content-Type).
Layered system: клиент может не знать, общается ли он с конечным сервером или с прокси, балансировщиком, кэшем.
Code on demand (необязательное): сервер может передать клиенту исполняемый код.

## Опорные вопросы: кто отправляет запрос и что получает? Что делают каталог, auth, корзина и заказы? Почему GET читает, а POST /orders меняет данные? Чем отличаются path, query и JSON? Приведите два своих запроса с ожидаемыми ответами.

Запрос отправляет клиент(фронтенд сайта, мобильная аппка, postman, swagger, другой сервис). Получает ответ(response), который содержит код ответа( 2хх, 4xx и т.д) и может содержать тело ответа как правило в JSON, либо XML.

Эндпоинты каталога возвращают списки брендов, продуктов, карточки товара. Админу доступны создание и удаление products.

Auth отвечает за регистрацию, логин пользователя.

Корзина - получение самой корзины(продуктов в ней), добавление продуктов, удаление продуктов из корзины.

Заказы - просмотр списка заказов, создание заказа из снимка корзины(не нужно отправлять тело запроса, только user_id). Админ может менять статус заказа.

GET запросы не меняют состояние сервера(не должны менять, конечно в коде мы можем написать что угодно) и их можно кэшировать. POST не идемпотентен(каждый запрос меняет состояние сервера) и его нельзя кэшировать. Но технически мы можем использовать POST для всего( не GET, т.к у него нету BODY и нельзя передать JSON объект, только path query параметры).

Path это путь к эндпоинту на сервере (/products). В path могут быть переданы параметры (/products/{product_id}) и это два пути отличаются, один ведет к получению списка всех продуктов, второй к конкретному продукту.

Query параметр передается после пути (/orders), указывается знак ? с указанием имени параметра (/orders?limit=20&offset=11). Несколько query параметров передаются через &.

JSON (JavaScript Object Notation) это текстовый формат для общения в сети(между сервисами, клиент-сервисом и т.д). Альтернативный формат XML(устарел, но часто исп. в банковской сфере). Поддерживает 6 типов значений: объект {}, массив [], строка, число, true/false, null. Пример ответа в JSON { "status": "closed", "comment": null }, либо массив объектов [{ "status": "closed", "comment": null }, { "status": "closed", "comment": null }].

## 2. База данных и связи

## Назовите семь таблиц. Объясните связи Brand → Product → ProductSize и Order → OrderItem. Где владелец корзины? Чем карточка товара 10 отличается от размера 101? Почему остаток находится у размера, а цена покупки — в позиции заказа?

Мой ответ:

brands	бренд
products	модели кроссовок
product_sizes	конкретный размер модели и его stock
users	пользователи
cart_items	product_size в корзине
orders	заказы
order_items	product_size в заказе


products.brand_id → brands.id. У бренда много моделей, у модели ровно один бренд (1 ко многим), потому что brands.id nullable=False.
product_sizes.product_id → products.id. У модели много размеров (1 ко многим). Ограничение UniqueConstraint(product_id, size) не даёт завести один размер дважды, поэтому остаток не может разойтись по двум строкам.

Тоже (1 ко многим): order_items.order_id → orders.id. orders — это заказ (кто купил, статус, итоговая сумма). order_items — его строки. Каждая строка ссылается на product_sizes.id, а не на products, потому что покупают конкретный размер.

Отдельной таблицы для корзины нету( связи с userId). Мы связываем товары в корзине с user_id(cart_items where userId = user.Id). UniqueConstraint(user_id, product_size_id) гарантирует, что у пользователя одна строка на каждый размер.

Карточка товара с Id 10 это продукт, а в корзину кладем конкретный размер product_sizes.id. По этой же причине остаток указан так же у product_sizes, а не products.

products.price — текущая цена, её может поменять администратор. order_items.price_at_purchase фиксирует цену одной пары в момент покупки.

## 3. Путь оформления заказа

## Откуда берутся пользователь, корзина, цена и сумма?

Клиент не присылает ни одно из этих значений. Тело запроса пустое или {}. OrderCreate с extra="forbid" отвечает 422 на любое лишнее поле, например user_id или total.

Пользователь. get_current_user_id (routers/auth.py) проверяет JWT и по его sub читает строку users. В сервис передаётся только user_id.
Корзина. Сервис читает cart_items WHERE user_id = user_id.
Цена. Берётся из products.price после блокировки этих строк.
Сумма. Сервис считает её сам как Decimal по ценам из БД. Затем проверяет, что она не больше предела Numeric(12,2).

##  Где транзакция начинается и кто делает commit?

Транзакцией управляет контекстный менеджер transaction().

открывает новую SessionLocal() и делает явный session.begin();
выставляет READ COMMITTED, а также SET LOCAL lock_timeout и statement_timeout;
при нормальном выходе из блока with делает один commit();
при любом исключении делает rollback();
в finally всегда вызывает close().
Внутри _create_order есть только flush(): он отправляет SQL в базу, но не фиксирует его. Роутер и сессия аутентификации commit не делают. Ответ 201 собирается уже после commit, поэтому он означает что заказ создан.

##  Что означают блокировки?

Блокировка строки (SELECT FOR UPDATE / FOR SHARE) держится до commit или rollback. Другая транзакция, которой нужна та же строка, ждёт.

1	users FOR UPDATE (блокировка владельца). Операции корзины и checkout одного пользователя выполняются по очереди. Корзина не меняется посреди оформления заказа.
2	product_sizes FOR UPDATE по возрастанию id. Остаток не меняется между проверкой и списанием. Два покупателя последней пары выстраиваются в очередь: второй после commit первого получает 409.
3	products FOR SHARE по возрастанию id. Цена не меняется, пока считается сумма. Читать строку другим можно, менять нельзя.
Все запросы берут блокировки в одном порядке: users → sizes → products, внутри таблицы по возрастанию id. Поэтому взаимные блокировки (deadlock) не возникают. Если блокировку не удалось получить за lock_timeout, клиент получает 409.

После commit блокировки снимаются.

## Что произойдёт, если второй позиции не хватает или ошибка возникла после очистки корзины?

На шаге 6( шаги помечены комментариеми ) сервис проверяет все позиции раньше первой записи. Если второй позиции не хватает, он выбрасывает OrderStockConflict, transaction() откатывает транзакцию, клиент получает 409. В базе не меняется ничего: нет заказа, остаток первой позиции не тронут, корзина на месте.

DELETE FROM cart_items выполнен, но commit ещё не был. Исключение выходит из блока with, и transaction() делает rollback. Откатывается заказ, позиции, списание остатков и удаление корзины. Корзина снова полная, клиент получает ошибку, а не 201.

Если commit прошёл, а ответ потерялся по сети. Клиент не знает, создан ли заказ. Автоматически повторять запрос нельзя: повтор вернёт 409 Cart is empty, а без Idempotency-Key нельзя надёжно узнать, каким был исход. Это делается через GET /orders.

##  Что меняется при успешных 101×2 +201×1?

Ответ — 201, в теле OrderRead позиции содержат subtotal 15980.00 и 5990.00. Повторный POST /orders вернёт 409 Cart is empty.

##  Почему перенос логики в сервис не должен разделить одну транзакцию на несколько commit?

Одна транзакция это один законченный этап бизнес логики, а несколько коммитов могут частично зафиксировать изменения, которых не должно быть в случае rollback.

## 5. Аутентификация и права

## Чем отличается хэш пароля от JWT?
Хэш лежит в базе - это bcrypt со случайной солью, необратимый ( нельзя из хэша получить пароль, только создать новый хэш + соль и сравнить с хэшем в базе).

JWT не хранится в базе, только на клиенте - это подписанный JSON: sub (id пользователя), exp (когда истекает), iat (когда выдан), iss (кто выдал), aud (для какого сервиса).

##   Что токен подтверждает и как сервер получает текущего User?

Цепочка _user_from_token (routers/auth.py:51):

BearerCredentials = Annotated[HTTPAuthorizationCredentials | None, Depends(bearer_scheme)] достаёт токен из заголовка. Нет заголовка → 401 Not authenticated.

decode_access_token:

проверяет подпись; алгоритм берётся из настроек, а не из заголовка токена, поэтому alg: none не пройдёт;
проверяет exp, iss, aud и наличие всех обязательных полей;
проверяет sub: только ASCII-цифры и значение в пределах int4.
Любая ошибка → 401.

get_user_by_id(session, sub) читает строку users из БД. Строки нет (пользователя удалили) → 401.

Дальше маршрут получает либо объект User (get_current_user), либо только его id (get_current_user_id для корзины и заказов).

## Почему роль читается из БД?

Роль админа могла быть отозвана после выдачи токена с правами админа. Чтобы права реально пропали нужно дождаться протухания токена и выдачи нового уже без прав Админа. А при чтении из бд права всегда актуальны.

##  Чем 401 отличается от 403?

401 это ошибка аутентификации, мы не знаем кто стучится в API.

403 мы знаем кто это(аккаунт существует), но прав доступа к конкретному эндпоинту нету ( нужны права админа к примеру)

##  Что произойдёт с чужим id корзины/заказа?

В коде запроса корзины есть условия where cart_items.user_id  = user_id, т.е найтись могут только товары в корзину для текущего пользователя, если их нету, то ответ 404.

##  Почему user_id из JSON нельзя считать владельцем?

Тело запроса целиком пишет клиент. Любой может отправить {"user_id": 1} с id чужого человека. Подпись есть только у токена, и только его сервер может проверить sub в нём выдал сам сервер после проверки пароля.

Владелец всегда берётся из токена (get_current_user_id) и передаётся в сервис отдельным аргументом userId.

(CartItemAdd, OrderCreate, ProductWrite) объявлены с extra="forbid". Если клиент пришлёт user_id, total или is_admin, он получит 422.

cart_items.user_id и orders.user_id записывает сервер, клиент на них не влияет.
